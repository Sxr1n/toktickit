# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing experience: a Requester (selected through a temporary
Development Requester selector) can create a Ticket with supporting attachments, find it again in My
Tickets via search/filter/sort/pagination, open its Ticket Detail, and manage its attachments — all while
one Requester can never see or affect another Requester's data.

## 2. Stakeholder Request Interpretation

The IT department wants proof that a real Requester can submit and track a support request end to end,
before IT Staff workflow exists. Since authentication isn't built yet, Lab 2 simulates "who is logged in"
with a Development Requester selector: the tester picks a seeded Requester, and every subsequent action
(create, list, view, attach) is scoped to that identity. This is explicitly a test harness, not security —
Lab 3 replaces it with real authenticated sessions without changing the underlying ownership model.

## 3. Scope

### Included
- Development Requester Selection screen (seeded, active Requesters only) and Change Requester action
- Create Ticket: Category, Related System, Summary, Description, Requested Priority, up to 5 attachments
- My Tickets: Requester-owned, paginated list with search, filters, and sorting
- Requester Ticket Detail: read-only Ticket header + Attachment list and actions
- Attachment lifecycle: add, download (active only), soft-remove with reason
- Ownership enforcement on every Requester-scoped read/write
- Zen Green UI system (colors, field states, validation placement, responsive rules) reused across all
  three screens
- Loading, empty, no-results, validation, and safe-failure states throughout

### Excluded (per labsheet §4.2)
- Authentication: login, logout, passwords, sessions, tokens, real role-based authorization
- IT Staff workflow: dashboard, queue, claiming/reassigning, IT Priority, ticket-owner functions
- Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle beyond initial creation (no resolve/close/reopen/cancel — status is always `New`)
- Administrator functions (user/reference-data management)

## 5. Business Rules

| ID | Rule |
|----|------|
| BR-01 | The official Ticket Number is generated by the backend and must be unique. |
| BR-02 | A new Ticket begins with Current Status `New`. |
| BR-03 | The Development Requester selector is a testing mechanism, not authentication. |
| BR-04 | A Ticket is always associated with exactly one Requester (the one selected at creation) and this association cannot be changed by the Requester. |
| BR-05 | A Requester may only view/list/modify Tickets and Attachments where `ticket.requesterId` equals the currently selected Requester's id; anything else returns a not-found/forbidden response without revealing existence. |
| BR-06 | The Requester selector lists only `isActive = true` Requesters; inactive Requesters cannot appear or be selected. |
| BR-07 | If the currently selected Requester becomes invalid on a later request (not found / inactive), the app returns to the Requester Selection screen. |
| BR-08 | Category and Related System values are loaded from the database, not hard-coded; only active values are selectable on Create Ticket. |
| BR-09 | Ticket Summary is required, trimmed, 5-150 characters. |
| BR-10 | Ticket Description is required, trimmed, 10-2000 characters. |
| BR-11 | Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`. |
| BR-12 | Ticket creation is validated on both frontend and backend; a backend validation failure creates no Ticket and returns field-level error detail. |
| BR-13 | The Submit button is disabled and shows a busy state for the duration of the request, preventing duplicate submission from one interaction. |
| BR-14 | If Ticket creation succeeds but an attachment upload fails, the Ticket is still saved; the failed attachment is reported clearly and can be retried later from Ticket Detail. |
| BR-15 | Allowed attachment types: JPG, JPEG, PNG, WEBP, PDF only; anything else is rejected before upload. |
| BR-16 | Maximum attachment size is 5 MB per file; larger files are rejected before upload. |
| BR-17 | A Ticket may have at most 5 active Attachments; a 6th active Attachment is rejected. |
| BR-18 | Removing an Attachment is a soft removal: the row is kept with `isRemoved=true`, `removedAt`, `removedReason`; the stored file is not deleted. |
| BR-19 | A removed Attachment's metadata stays visible on Ticket Detail; its download/preview controls are disabled. |
| BR-20 | Only the Requester who owns the Ticket may add or remove an Attachment on it. |
| BR-21 | Removing an Attachment requires a non-empty reason (min 3 characters) and an explicit confirmation step. |
| BR-22 | Default Ticket list sort is Ticket Date descending, with Ticket ID descending as a tiebreaker. |
| BR-23 | Ticket list page size is bounded (default 10, max 50); an invalid/out-of-range page or pageSize falls back to the default instead of erroring. |
| BR-24 | An invalid filter or sort parameter is ignored (falls back to default) rather than failing the request. |
| BR-25 | Search matches Ticket Number and Summary, case-insensitive, partial match. |
| BR-26 | Switching the Development Requester immediately invalidates the previous Requester's ticket data in the UI and reloads My Tickets for the new Requester. |
| BR-27 | If no active Development Requesters exist, the Requester Selection screen shows an empty state and disables Continue. |
| BR-28 | All Lab 2 authorization compares the client-declared selected-Requester id against `ticket.requesterId` on the backend. This is an explicit, temporary substitute for real auth and must be replaced by session-based authorization in Lab 3. |

## 7. Data Changes

Builds on Lab 1's `Category` model. New models (Prisma):

```prisma
model RequesterUser {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

enum Priority {
  LOW
  MEDIUM
  HIGH
}

enum TicketStatus {
  NEW
}

model Ticket {
  id                Int           @id @default(autoincrement())
  ticketNumber      String        @unique
  requesterId       Int
  requester         RequesterUser @relation(fields: [requesterId], references: [id])
  categoryId        Int
  category          Category      @relation(fields: [categoryId], references: [id])
  relatedSystemId   Int
  relatedSystem     RelatedSystem @relation(fields: [relatedSystemId], references: [id])
  summary           String
  description       String
  requestedPriority Priority
  currentStatus     TicketStatus  @default(NEW)
  createdAt         DateTime      @default(now())
  updatedAt         DateTime      @updatedAt
  attachments       Attachment[]

  @@index([requesterId])
  @@index([categoryId])
}

model Attachment {
  id             Int       @id @default(autoincrement())
  ticketId       Int
  ticket         Ticket    @relation(fields: [ticketId], references: [id])
  originalName   String
  storedName     String
  mimeType       String
  sizeBytes      Int
  uploadedAt     DateTime  @default(now())
  isRemoved      Boolean   @default(false)
  removedAt      DateTime?
  removedReason  String?

  @@index([ticketId])
}
```

Decisions: `ticketNumber` is a separate unique string (not the raw id) so it can carry a human-readable
format (see §11). `storedName` is a generated-safe filename distinct from the user's `originalName`, so
path traversal / collisions never depend on user input. Soft removal lives on `Attachment` itself rather
than a separate table — simplest option that still satisfies "retained metadata, blocked access."

## 8. API Contract

Full detail (request/response bodies, statuses) lives in `api-spec.md`. Endpoint list:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/categories` | List active Categories (reused from Lab 1) |
| GET | `/api/related-systems` | List active Related Systems |
| GET | `/api/dev-requesters` | List active Development Requesters |
| POST | `/api/tickets` | Create a Ticket for the selected Requester |
| GET | `/api/tickets` | Paginated, searchable/filterable/sortable list of the selected Requester's Tickets |
| GET | `/api/tickets/:id` | One owned Ticket's detail |
| POST | `/api/tickets/:id/attachments` | Upload an Attachment to an owned Ticket |
| GET | `/api/tickets/:id/attachments/:attachmentId` | Attachment metadata |
| GET | `/api/tickets/:id/attachments/:attachmentId/download` | Download an active Attachment |
| PATCH | `/api/tickets/:id/attachments/:attachmentId/remove` | Soft-remove an Attachment (body: reason) |

Every Requester-scoped endpoint requires an `X-Dev-Requester-Id` header identifying the currently
selected Requester (see §11). The backend validates it against an active `RequesterUser` and uses it as
the ownership filter on every query.

## 11. Assumptions and Decisions

- **Requester identity transport**: since there's no session, the selected Requester id travels as an
  `X-Dev-Requester-Id` request header, validated server-side on every request. Chosen over a query param
  because it keeps the "identity" concept separate from each endpoint's own filters/params.
- **Ticket Number format**: `TKT-{YYYY}-{6-digit sequence}` (e.g. `TKT-2026-000123`), matching the format
  shown in the Lab 1 handout's illustrative screen. Uniqueness enforced at the database level.
- **`TicketStatus` as an enum with a single `NEW` value** (rather than a free-text string) — keeps the
  field type-safe now and only needs a Prisma migration, not a data-shape change, when later labs add
  more statuses.
- **Soft removal** is a boolean + timestamp + reason on `Attachment` directly, not a separate audit table
  — sufficient to satisfy "retained metadata, blocked access" without over-engineering for Lab 2's scope.
- **Pagination defaults**: page size 10, max 50, to keep My Tickets responsive without the student having
  to define arbitrary business-specific limits.
